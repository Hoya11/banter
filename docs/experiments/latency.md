# 지연 측정

이 문서는 2026-08-25와 2026-08-26의 구현 변경 및 당시 관찰을 기록한다. 구간마다 측정 시작점과 끝점이 다르며, 소수 표본의 로컬 관찰 기록이다. p95와 일반적인 사용자 체감 성능은 미검증.

## 2026-08-25 - prefetch 도입 전후

환경: gpt-5.6-luna(발화) + gpt-4o-mini(supervisor) + ElevenLabs v3(TTS), 로컬 WS 실측 3턴.

측정 항목은 발화 재생 완료(`played` ack)부터 다음 발화 오디오 도착까지의 간격이다. AI끼리 대화하는 턴 사이의 대기를 보기 위한 지표이며, 사용자 발화에 대한 응답 시간이나 실제 스피커 출력 간격을 측정한 값은 아니다.

| 구성 | 발화 간 간격 | 비고 |
|---|---|---|
| prefetch 없음 (직렬) | ~8s | 당시 대략적인 구간 기록: radio 5s, supervisor ~1s, 생성 ~1.5s, v3 합성 2~4s |
| prefetch (병렬) | 평균 2.09s (1.52 / 2.88 / 1.87) | radio 틈 1.5s 포함. 이를 뺀 준비 대기 평균 ~0.6s, 최저 0.02s |

prefetch 도입과 함께 radio 대기도 5s에서 1.5s로 줄었다. 따라서 약 8s에서 평균 2.09s로 바뀐 전체 차이를 prefetch 단독 효과로 해석할 수 없다. 직렬 구성의 약 8s와 구간별 값은 당시 대략적인 기록으로, 정밀한 구간별 합산 결과는 이 문서에 남아 있지 않다. 효과를 분리하려면 radio 대기와 모델, 대화 조건을 고정한 비교가 필요하다.

### 구조

- 발화 A가 재생되는 동안 백그라운드에서 다음 턴(화자선정→대사→합성)을 완성해 둔다.
- 유저 개입 시 미리 만든 응답을 폐기하고 새 입력에 반응한다. 이미 생성·합성이 완료된 경우 LLM+TTS 1회분의 비용이 사용되지 않은 응답에 들어간다.
- 재생 페이스는 FE `played` ack를 기준으로 맞춘다.

### 관찰

- 관찰한 3턴에서는 다음 응답 준비를 현재 재생과 겹쳐 수행했고, 의도된 대기 1.5s를 제외한 준비 대기가 가장 짧은 턴에서 0.02s였다. 관찰 중 최솟값이며 전체 턴의 지연 분포는 미측정.
- 2.88s 케이스는 당시 v3 합성이 재생 시간(3s 가정)보다 오래 걸려 대기가 남은 것으로 해석했다. 발화가 길면 겹쳐 처리할 시간도 늘지만, 그만큼 합성 시간도 달라질 수 있어 추가 측정이 필요하다.
- 평균 2.09s에는 의도된 유저 발언 틈 1.5s가 포함된다. 이 설정은 처리 속도와 별도로 대화 리듬에 영향을 준다.

### 다음

- 유저 발화부터 첫 응답까지의 지연을 별도로 측정한다. 새 입력을 반영해야 하므로 AI끼리 대화하는 턴의 prefetch 결과로 대신 평가할 수 없다.
- 세션 단위 p50/p95 자동 수집(Langfuse trace) 및 턴당 비용 병기.

## 2026-08-26 - 유저 응답 경로의 한계 (실사용 발견, Phase 3 착수 근거)

push-to-talk 실사용에서 "말해도 바로 전달이 안 되는 느낌"을 관찰했다. 당시 파일 전사와 발화 전체 합성 경로를 다음과 같이 나누어 보았다. 아래 값은 병목 후보를 찾기 위한 대략적인 기록이며, 표본 수와 분포를 갖춘 지연 측정 결과는 아니다.

| 구간 | 지연 | 비고 |
|---|---|---|
| 버튼 뗌 → 전사 완료(whisper) | ~1s+ | 이 동안 화면 무반응 — 인지된 지연 가중 |
| supervisor + 발화 생성 | ~2s | |
| TTS(v3) 발화 통째 합성 | 2~4s | 최대 병목 |
| 합계 (버튼 뗌 → 첫 소리) | 5~8s | 당시 체감 경로의 대략적인 기록. 목표 p95 < 1.5s와 직접 비교할 p95 실측은 없음 |

초기 기록의 목표 대비 3~5배 초과 표현은 대략적인 관찰값 5~8s와 p95 목표를 비교한 오류였다. p95 미측정으로 목표 대비 초과 비율은 미확인.

### 구조적 관찰

- **prefetch 적용 범위**: AI끼리 턴은 미리 준비했지만, 유저 응답 턴은 새 발화를 반영해 생성해야 한다. 앞서 관찰한 약 2s는 AI 간 간격이며, 유저 응답 경로는 별도 측정 대상이다.
- **당시 파일 전사 방식의 한계**: 녹음이 끝난 뒤 파일을 보내므로 말하는 동안 전사를 진행하지 못했다. 이는 버튼 조작 자체의 제약은 아니며, push-to-talk를 유지한 채 스트리밍 STT를 적용하는 방식도 가능하다.
- **발화 단위 TTS의 한계**: 문장 2개를 모두 합성한 뒤 오디오를 보내고 있었다. 문장 단위로 쪼개면 전체 발화의 합성이 끝나기 전에 첫 문장 오디오를 보낼 수 있다.

이 관찰을 근거로 Phase 3에서 전사와 합성의 대기를 줄이는 변경을 검토했다. 반응 필러는 기다리는 느낌을 바꿀 수 있지만, 위 처리 구간 자체를 줄이지는 않으므로 먼저 처리 구조를 개선하기로 했다.

## 2026-08-26 - Phase 3a: 문장 단위 TTS 스트리밍

LLM 토큰 스트림에서 문장 경계를 실시간 감지, 첫 문장 완성 즉시 합성·전송.
둘째 문장은 첫 문장이 재생되는 동안 생성·합성(턴 내부 파이프라이닝).
문장 상한에 도달하면 LLM 스트림을 조기 중단한다. 토큰 비용 감소량은 이 기록에서 측정하지 않았다.

| 지표 | 3a 이전 | 3a 이후 (실측) |
|---|---|---|
| 유저 say → 첫 오디오 | ~4-6s (발화 전체 생성+합성) | **~2.4s** (웜), 4.9s(콜드 1회) |

- 이번 측정의 입력은 텍스트 `say`이므로 STT 시간이 포함되지 않는다. 실제 스피커에서 첫 소리가 나는 시각을 검증한 결과도 아니다.
- 측정 3회 중 1회(0.00s)는 직전 턴의 잔여 문장 오디오가 겹쳐 제외했다. 유효 관찰은 2회이며, p95와 반복 실행의 개선율은 미산출.
- 목표 p95 < 1.5s 달성은 아직 확인하지 못했다. 텍스트 입력 경로에는 supervisor, 첫 문장 생성, v3 합성의 대기가 남았다. 당시에는 짧은 문장도 합성에 2~3s가 걸리는 것을 관찰했다.
- 다음 후보는 3b의 스트리밍 STT와 응답 첫 문장에 적용할 저지연 TTS(flash) 비교였다. 스트리밍 STT는 음성 입력 경로를 위한 변경으로, 이번 텍스트 입력 측정과는 검증 대상이 다르다.
