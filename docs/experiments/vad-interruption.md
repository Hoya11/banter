# VAD 끼어들기 실험

## 목적과 현재 근거

banter는 사용자 한 명이 AI 둘의 대화를 듣다가 참여하는 음성 대화입니다. 이번 단계의 가설은
발화마다 버튼을 누르고 놓는 대신 말로 참여할 수 있으면 사용 흐름이 자연스러워진다는 것입니다.
버튼 조작의 불편을 정량 관찰한 기록이나 VAD 도입 후 개선 수치는 아직 없습니다.

기존 push-to-talk는 버튼을 누른 즉시 브라우저 오디오를 중단하고 서버에 `hold`를 보냅니다.
스트리밍 STT는 말하는 동안 PCM을 전송하고 버튼을 놓으면 commit합니다. VAD가 추가하는 것은
이 두 경계의 자동 판단입니다. STT가 더 빨라졌다거나 기존 pause 경로 자체가 빨라졌다는 주장과
구분합니다. 자동 감지의 편의가 오감지, 놓친 발화와 잘못된 종료의 비용을 넘는지 확인합니다.

## 비교한 선택지

| 선택지 | 적용 이유 | 이번 단계에서의 판단 |
| --- | --- | --- |
| Push-to-talk 유지 | 시작과 종료를 사용자가 명시하고 현재 동작과 비교 가능 | 기본값과 비교 기준으로 보존 |
| 클릭 시작과 클릭 종료 | 버튼을 계속 누르는 부담을 줄임 | 수동 경계의 대안이며 아직 구현하거나 비교하지 않음 |
| RMS 음량 기준 감지 | 신호 크기를 기준으로 작은 실험을 만들 수 있음 | 음량만으로 말과 다른 소리를 구분하지 않으므로 채택하지 않음. 측정 비교는 아직 없음 |
| 브라우저 Silero VAD | 브라우저에서 말 확률을 얻고 로컬 재생 중단과 연결 | 선택 모드로 구현. 소음 환경의 품질은 실제 측정 필요 |
| 서버 또는 공급자 VAD | 말 경계 판단을 서버에서 처리 | 말 시작 전 오디오 전달과 감지 결과 전달 경로가 필요하여 이번 범위에서 제외 |
| 의미 기반 턴 종료 | 생각하는 중의 침묵과 완료된 발화 구분 | 말 시작 감지와 별도 문제. 잘못된 종료가 남을 때 후속 검토 |

이 표는 실측 성능 순위가 아닙니다. 원격 VAD보다 브라우저 VAD가 실제로 얼마나 빠른지 비교한
결과도 없습니다. 현재 브라우저 오디오 중단 경로를 활용하면서 침묵 중 공급자 전송을 피하는
범위로 실험을 제한하기 위해 브라우저 방식을 선택했습니다.

WebRTC는 VAD 방식과 별도의 전송 선택입니다. 현재 WebSocket을 유지하고 먼저 감지 품질을
확인합니다. 전송 지연, 지터와 에코가 병목으로 확인될 때 WebRTC 또는 LiveKit을 검토합니다.

## 실행 방식과 상태 경계

`BANTER_INTERACTION_MODE=vad`와 `BANTER_STT_MODE=streaming_push_to_talk`를 함께 설정합니다.
설정을 바꾸지 않은 기본 실행은 push-to-talk와 파일 전사입니다. VAD와 파일 전사를 함께
설정하면 서버가 시작 설정 오류로 알립니다. 서버의 `hello.interaction_mode`와 `hello.vad`
capability로 브라우저 모드를 선택합니다. VAD에서는 `대화 시작`을 누르면 마이크와 모델을
먼저 준비하고 준비 완료 뒤 `session_start`를 보냅니다. 준비 취소나 권한 거부 시에는 AI
대화를 시작하지 않습니다. 대화 중에는 마이크 버튼으로 지속 감지를 끄거나 다시 켭니다.
마이크 끄기, 세션 종료 또는 연결 종료 시 청취 자원을 정리합니다. 장치 연결 해제나 권한 회수로
마이크 입력이 종료되어도 청취와 진행 중인 발화를 취소하고 다시 켤 수 있는 상태로 돌아갑니다.
이때 불완전한 발화를 commit하지 않으며, 이전 마이크의 늦은 종료 이벤트는 무시합니다.

| 기존 경로와 공유 | VAD에서 별도 관리 |
| --- | --- |
| 발화별 `client_event_id`, 세션과 요청 유효성 검사 | 마이크 활성화와 지속 청취 수명 |
| `hold`, 브라우저 pause와 늦은 오디오 억제 | 말 시작 후보, 시작 확정과 침묵 종료 판정 |
| PCM 청크 순번, 잔여 청크 전송과 명시적 commit | 발화 직전 오디오 버퍼와 확률 모델 상태 |
| 최종 전사, 텍스트 우선 처리, 취소와 오류 복구 | 감지 시각, 감지 이벤트의 세대와 재진입 |

기존 push-to-talk worklet은 flush 후 입력을 닫고 녹음 자원을 정리합니다. 따라서 VAD의 지속
청취 상태를 버튼 눌림이나 발화별 PCM 캡처와 같은 상태로 취급하지 않습니다. 청취와 발화 요청을
분리하되, 말 시작은 기존 중단 경로로, 말 종료는 공통 commit 경로로 연결합니다.

말 감지는 Silero v5를 사용합니다. `@ricky0123/vad-web` 0.0.30과 `onnxruntime-web` 1.22.0을
고정하고 프로젝트 루트에서 다음과 같이 로컬 제공 파일을 준비합니다.

```bash
cd web
npm ci --ignore-scripts
npm run prepare:vad
```

의존성의 공식 출처는 [vad-web 저장소](https://github.com/ricky0123/vad)와
[ONNX Runtime 저장소](https://github.com/microsoft/onnxruntime)입니다. 현재 동작은 설치한
고정 버전의 코드를 기준으로 확인하며, 버전 변경 시 다시 검증합니다.

모델과 실행 파일은 `web/vendor/vad/`에 준비하며 앱 서버의 `/vad-assets/`에서 제공합니다.
실행 중 모델 추론은 브라우저에서 수행합니다. 침묵 중에는 STT 공급자에 오디오를 계속 보내지
않습니다. 실제 서버 실행에서 발화로 판단한 오디오와 직전 버퍼가 기존 스트리밍 STT 공급자로
전달됩니다. 감지 취소가 공급자 사용량 0을 보장하는 것은 아닙니다. 발화 시작 후 이미 보낸
오디오가 있을 수 있습니다.

MicVAD는 브라우저 입력을 16 kHz로 변환해 모델에 전달합니다. 어댑터는 선택한 발화와 직전
버퍼를 연속 보간으로 24 kHz로 변환하여 기존 PCM 전송 경로에 연결합니다. Push-to-talk는
기존 24 kHz AudioWorklet 경로를 사용하므로 두 모드의 입력 바이트는 동일하지 않습니다.
실측에서 전사 정확도 차이가 생기면 자동 경계뿐 아니라 이 오디오 변환 경로도 함께 점검합니다.

초기 설정은 시작 확인 160 ms, 종료 침묵 600 ms, 발화 직전 버퍼 256 ms입니다. 시작은 말 확률
0.6 이상인 5개 연속 프레임, 종료는 말 확률 0.35 미만인 19개 연속 프레임으로 판단합니다.
모델 입력의 512 sample, 16 kHz 프레임에 맞추므로 종료 침묵은 실제로 608 ms입니다.
시작 전 버퍼에는 시작 후보 구간도 함께 보존합니다. 아직 환경별 정확도나 최적 지연을 검증한
값이 아닙니다. 발화 오디오가 12초에 도달하면 그 요청을 취소하고 감지를 다시 준비합니다.
기존 서버의 15초 hold와 오디오 길이 제한을 늘리지 않습니다. 취소 후에는 종료 침묵 구간을
확인한 뒤 다시 감지하여 같은 긴 발화를 곧바로 새 요청으로 나누지 않습니다.

이 모델은 본인 목소리나 끼어들 의도를 식별하지 않습니다. 주변 사람의 말, 맞장구, TV 음성과
AI의 스피커 출력이 감지될 수 있습니다. 첫 비교는 헤드폰으로 수행하고 스피커 조건을 별도로
확인합니다. 브라우저의 에코 제거 요청만으로 이 문제가 해결됐다고 보지 않습니다.

## 검증 범위

현재 Python 테스트 217개와 웹 테스트 122개가 통과했습니다. 웹 테스트는 화면 상태 55개,
VAD 어댑터와 공유 판단 코드 29개, 녹음 평가 38개입니다. Python 전체 실행은 Node.js가 있으면
웹 테스트도 호출하므로 두 건수를
별도 독립 실행 건수처럼 합산하지 않습니다. 전체 테스트 전 `web`에서 `npm ci --ignore-scripts`로
의존성을 준비해야 합니다.

2026-09-18에는 전송 지연 중 취소와 다음 입력 처리, 응답 없는 연결 종료를 추가로 검증했습니다.
VAD와 push-to-talk가 공유하는 서버 경로의 수정 이유와 모의 검증 결과는
[스트리밍 STT 복구 기록](streaming-stt-ab.md#전송-지연과-연결-종료-복구)에 정리합니다.

자동 테스트는 가짜 발화 확률, PCM, 공급자와 시간을 사용하여 상태 전이를 확인합니다.
고정된 실제 MicVAD와 FrameProcessor에 가짜 순환 모델을 연결한 회귀 테스트도 포함합니다.
어댑터가 라이브러리의 오디오 버퍼를 비우더라도 확률 처리와 모델 상태가 유지되는지 확인하며,
라이브러리의 내부 구조를 사용하는 부분은 버전을 올릴 때 다시 검수해야 합니다.

별도의 로컬 Chrome 152.0.7977.82 확인에서는 실제 Silero ONNX 모델과 WASM 실행 파일을
불러오고 가상 마이크를 켜고 끄는 경로를 검증했습니다. 이 브라우저 확인에서 외부 요청은
발생하지 않았습니다. 실제 OpenAI 또는 ElevenLabs 호출, 실제 사용자 마이크 입력, 소음 환경의
정확도나 체감 지연 측정을 대신하지 않습니다. 모델 로딩과 가상 마이크 동작을 확인했다는 사실도
사용자 음성 품질 측정 완료를 뜻하지 않습니다.

2026-09-08에는 같은 Chrome에서 macOS Yuna로 로컬 합성한 한국어 문장의 48 kHz WAV를
가상 마이크 입력으로 사용했습니다. 실제 Silero가 발화 2개의 시작과 끝을 감지하고, 공통 PCM
경로에서 순서가 있는 청크, 마지막 잔여 청크, commit과 가짜 STT의 최종 결과까지 이어지는 것을
확인했습니다. 외부 HTTP 요청이나 페이지 오류는 없었습니다. 이 확인은 합성 입력의 통합 동작
검증이며 실제 마이크와 에코 품질, 실제 전사 정확도 또는 지연 측정 결과가 아닙니다.

검수 시 확인할 사례는 다음과 같습니다.

- 시작 확인 시간보다 짧은 소음 후보가 `hold`와 전송을 만들지 않는지 확인합니다.
- 발화 중 짧은 침묵이 같은 요청으로 이어지고 종료 침묵 이후에만 commit되는지 확인합니다.
- 발화 앞부분 버퍼와 마지막 PCM 청크가 순서대로 보내지는지 확인합니다.
- 긴 발화, 오류와 사용자의 마이크 끄기 뒤 다음 시도가 가능한지 확인합니다.
- 대기, 발화 또는 초기화 도중 마이크 입력이 종료되면 취소하고 재시도할 수 있는지 확인합니다.
- 이전 감지 이벤트, 지연된 마이크 초기화, 전사 결과가 새로운 세션이나 요청을 침범하지 않는지 확인합니다.
- 텍스트 입력이 음성 요청보다 우선하며 기존 push-to-talk 테스트가 유지되는지 확인합니다.

## 첫 실사용 오류와 수정

2026-09-10 사용자 테스트에서 마이크를 켜는 동안 이미 AI가 말하기 시작했고, 끼어든 음성의
확정 처리에서 `ConnectionClosedError`가 보고됐습니다. 다른 AI가 대화를 이어갔으며 이후
말도 인식되지 않았다는 관찰이 있었습니다. 감지 모델 파일은 HTTP 200으로 로드됐습니다.
이 기록은 오류 관찰이며 지연이나 인식률 측정 결과는 아닙니다.

코드와 재현 테스트에서 다음 문제를 확인했습니다.

- `hello`를 받자마자 `session_start`를 보내 마이크 준비와 AI 시작 순서가 뒤집혀 있었습니다.
  VAD에서는 마이크 시작 완료를 기다린 뒤 AI 세션을 시작하도록 변경했습니다.
- 종료된 발화의 STT 오류가 감지기를 다시 초기화해 추가 침묵을 요구하고, 다음 발화의 시작
  후보까지 지웠습니다. 종료된 요청의 오류와 시간 초과에서는 감지 상태를 유지합니다.
  아직 진행 중인 발화 취소나 최대 길이 초과에서는 기존 침묵 대기를 유지합니다.
- 공급자가 보낸 오류 뒤 commit 전송에서 연결 오류가 발생하면 앞선 오류가 가려질 수
  있었습니다. 이미 받은 오류를 우선 보존하고, 오류 발생 단계, 공급자 오류 코드와 WebSocket
  종료 코드를 로그에 추가했습니다. 키, 전사, 오디오, 원문 오류 메시지는 기록하지 않습니다.

현재 세션 설정은 [OpenAI Realtime transcription 공식 문서](https://developers.openai.com/api/docs/guides/realtime-transcription)의
`gpt-live-transcribe`, 24 kHz PCM, 수동 commit, `languages`와 `delay` 예시와 일치했습니다.
이 대조는 설정 본문에 관한 것이며 연결 성공을 확인한 결과가 아닙니다. 최초 로그만으로는
연결 종료의 실제 원인을 확정할 수 없었습니다.

가짜 공급자가 실제 `ConnectionClosedError` 클래스를 발생시킨 서버 테스트에서는 같은
WebSocket으로 다음 발화를 받을 수 있었습니다. 오류 뒤 AI 대화 재개는 기존 동작이며,
기본 12회 AI 발화 제한에 도달하면 세션이 종료됩니다. 사용자 사례가 감지기의 추가 침묵 대기
때문인지 세션 종료까지 겹쳤는지는 실사용 재확인이 필요합니다. 이번 수정 검증은 가짜 공급자,
가짜 발화 확률과 로컬 브라우저로 수행하며 외부 음성 API를 추가 호출하지 않습니다.

## 연결 생성 단계 재검증

후속 사용자 로그에서 `stage=configure`, 수신 및 송신 종료 코드 `4000`을 확인했습니다.
서버의 확정 처리 안에서 아직 끝나지 않은 공급자 시작 작업을 기다리므로, 로그 제목이
확정 실패여도 실제로는 세션 생성이나 설정 단계의 실패일 수 있습니다. `4000`만으로 모델
권한, 결제 상태, 잘못된 연결 설정 중 어느 것이 원인인지 단정하지 않습니다.

기존 연결은 `?model=gpt-live-transcribe`로 시작했습니다. 전사 모델을 세션의 입력 전사 설정뿐
아니라 연결 주소의 대화 모델 자리에도 넣고 있었습니다. [공식 STT 비교 예제](https://developers.openai.com/cookbook/examples/speech_transcription_methods)의
Realtime 전사 연결 주소는 `?intent=transcription`입니다. 해당 예제에는 Beta용 본문과 헤더도
있으므로 이를 그대로 복사하지 않고, 연결 목적만 명시하며 현재 가이드의 `session.update`,
`session.type=transcription`, `audio.input.transcription.model=gpt-live-transcribe`를 유지합니다.
모델 교체나 WebRTC 전환은 하지 않습니다.

또한 WebSocket 연결 직후 `session.update`부터 보내면, 서버가 오류를 보낸 뒤 연결을 닫았을 때
전송 예외가 먼저 나서 오류 응답을 읽지 못할 수 있었습니다. 이제 먼저 `session.created`를
받고 전사 세션인지 확인합니다. 초기 오류는 `stage=session_create`로 보존하며, 잘못된 유형의
세션에는 오디오를 보내지 않습니다. 생성 대기부터 설정 확인까지 하나의 제한 시간을 적용합니다.

검증은 실제 설치된 OpenAI SDK의 전송 경계를 가짜 WebSocket으로 대체해 수행합니다. 연결 URL,
이벤트 직렬화, 서버 응답을 기다리는 순서와 초기 오류 보존을 확인하며 원격 모델은 호출하지
않습니다. 따라서 연결 방식 수정 후 실제 서비스가 정상 전사했다는 결론은 아직 내리지 않습니다.
다음 실사용에서 공급자 오류 코드 또는 세션 생성 이후 단계까지 진행하는지 확인해야 합니다.

2026-09-14 추가 조사에서는 세션 생성 응답을 받은 뒤 설정을 보내는 순간에도 오류가 가려질
수 있음을 재현했습니다. 공급자의 `error` 이벤트가 수신 대기열에 남아 있어도 `send()`가 먼저
연결 종료를 보고하면 기존 로그에는 `4000/configure`만 남았습니다. 실제 사용자 오류가 같은
순서였다는 증거는 아니며, 진단 정보가 누락될 수 있다는 모의 재현 결과입니다.

이제 설정 전송과 확인 응답 대기를 `configure_send`, `configure_ack`로 구분합니다. 설정 전송
도중 연결이 닫히면 최대 100 ms 동안 이미 받은 공급자 오류를 확인해 안전한 오류 유형, 코드,
필드 이름과 종료 코드를 보존합니다. 이 시간은 전체 연결 설정 기한에도 포함됩니다. 오류가
없거나 확인에 실패하면 원래 연결 종료 정보를 유지하며, 사용자의 취소를 막지 않습니다.
원문 오류 메시지, 종료 사유, API 키와 오디오는 로그에 추가하지 않습니다.

현재 연결 주소와 설정 본문은 실제 설치된 SDK를 통과한 모의 전송으로 확인했습니다. 이 검증은
모델 사용 권한, 계정 상태 또는 원격 서버의 연결 성공을 확인한 결과가 아닙니다. 실제 연결을
확인할 때도 전체 AI 대화를 시작하기 전에 전사 세션 생성과 설정 확인만 분리해 검사할 수 있습니다.

## 실측 절차

실제 마이크를 사용할 수 없을 때는 [녹음 VAD 평가 도구](vad-recording-evaluation.md)로
같은 WAV의 종료 설정을 비교할 수 있습니다. 녹음 평가 결과와 아래 라이브 실측은 구분합니다.

실제 공급자를 호출하기 전에 결제 상태, 지출 상한, OpenAI 및 필요한 경우 ElevenLabs 키,
예상 세션 수, 사용자 발화 수, AI 턴 수와 오디오 길이를 먼저 설명하고 실행 범위를 정합니다.
키 값과 원본 실행 로그는 Git에 넣지 않습니다. 예산 확인 없이 API 호출로 테스트를 확대하지 않습니다.

같은 기기, 브라우저 버전, 마이크, 출력 장치와 음량, 네트워크, 모델, 시나리오를 기록합니다.
파일 전사와 스트리밍 전사를 비교할 때는 push-to-talk를 유지합니다. VAD를 비교할 때는
스트리밍 STT를 고정하여 전사 방식과 자동 감지의 효과가 섞이지 않도록 합니다.

고정 시나리오는 AI 재생 중 명확한 끼어들기, AI가 조용할 때 발화, 짧은 맞장구, 문장 중간의
짧은 침묵, 긴 생각 멈춤, 키보드와 생활 소음, 주변 사람의 발화, 마이크 켜기와 끄기 및 재시도로
구성합니다. 헤드폰과 스피커 조건은 섞지 않고 각각 집계합니다.

실제 발화 시작과 끝, 끼어들 의도는 녹음 또는 화면 관찰을 바탕으로 수동 표시합니다.
말한 사람과 발화 구간을 확인할 수 없는 샘플을 추측으로 라벨링하지 않습니다. 원본 녹음을 남길
범위와 보관 위치는 측정 전에 정하고 공개 문서에는 민감한 대화나 키를 넣지 않습니다.

## 지표와 분모

| 지표 | 계산과 분모 | 주의점 |
| --- | --- | --- |
| 감지 후 브라우저 중단 지연 | 말 시작 확정부터 pause 적용까지, 실제 재생 중이며 `paused`인 표본 | 감지 자체의 대기와 실제 스피커 출력 지연은 포함하지 않음 |
| 실제 발화 후 중단 지연 | 수동 표시한 발화 시작부터 브라우저 pause 또는 실제 출력 중단까지 | 두 종료점을 별도 집계. 못 잡은 발화는 실패 건수로 남김 |
| 말 끝 판정 대기 | 수동 표시한 발화 종료부터 종료 판정까지 | 종료 침묵 설정이 만드는 대기를 포함 |
| 종료 판정 후 최종 전사 지연 | 종료 판정부터 일치하는 최종 전사 관찰까지 | 실제 말 끝부터 전사까지의 전체 지연과 별도 집계 |
| 잘못된 발화 시작 비율 | 의도된 사용자 발화와 맞지 않는 시작 확정 수 / 전체 시작 확정 수 | 사람이 판정. 짧다는 이유만으로 오감지로 세지 않음 |
| 시간당 불필요한 중단 | 의도된 사용자 발화 없이 AI 재생을 중단한 횟수 / 마이크 활성 시간 | 시작 비율과 함께 제시하여 환경별 노출 시간을 반영 |
| 놓친 발화 시작 비율 | 감지 시작과 대응하지 않는 의도된 사용자 발화 수 / 의도된 사용자 발화 수 | 감지 성공 사례만으로 지연을 평가하지 않음 |
| 발화 중간 절단 비율 | 끝나기 전 commit 또는 제한 취소가 발생한 사용자 발화 수 / 의도된 사용자 발화 수 | 조기 종료와 최대 길이 취소의 원인을 나눠 집계 |
| 재시도 부담 | 잘못된 감지 또는 전사 때문에 다시 말한 발화 수 / 의도된 사용자 발화 수 | 사용자 관찰 기준과 원인을 함께 기록 |

지연은 표본 수와 p50, p95를 함께 제시합니다. 표본이 없는 경우 0 ms로 쓰지 않습니다.
대기열만 비웠거나 재생할 항목이 없던 경우, pause 실패, 전사 실패와 시간 초과는 별도 건수로
남깁니다. 브라우저와 서버의 서로 다른 시계 값을 직접 빼지 않고 같은 시계에서 잰 구간이나
상관 ID로 확인한 이벤트를 사용합니다.

PTT 버튼 해제 시각과 VAD 종료 판정 시각은 다른 기준입니다. 이 둘부터 최종 전사까지의 값만
비교하여 전체 개선이라고 주장하지 않습니다. 실제 발화 종료부터의 전체 시간과 종료 판정
대기를 함께 봅니다. 실제 출력 중단은 별도의 오디오 관찰이 필요하며 `Audio.pause()` 반환으로
대체하지 않습니다.

## 이벤트 요약

`BANTER_EVENT_LOG`로 JSONL 기록을 켜고 세션이 끝난 뒤 서버 디렉터리에서 실행합니다.

```bash
PYTHONPATH=. uv run python scripts/summarize_vad.py artifacts/runs/dev.jsonl
```

브라우저의 `vad_observed` 시작과 종료 관찰은 `vad_speech_started`와 `vad_speech_ended`로
남습니다. 요약의 `vad_start_to_audio_stop_ms`와 `vad_end_to_final_ms`는 각각 감지 이후
pause와 최종 전사까지의 구간입니다. VAD 표본을 PTT 버튼 시점 지표에 섞지 않습니다.
`audio_stop_outcomes`에는 `paused`, `idle`, `pause_failed` 등 오디오 중단 결과별 건수를,
`stt_outcomes`에는 `success`, `empty`, `error` 등 전사 결과별 건수를 남깁니다. 결과 이벤트가
없는 표본은 임의로 성공이나 실패로 분류하지 않고 `missing_events`에서 확인합니다.
사람의 정답 라벨이 없는 오감지와 중간 절단율은 미측정으로 남기며 취소 건수를 오감지율로
바꾸지 않습니다. 놓친 발화도 자동 로그만으로 알 수 없으므로 수동 기록이 필요합니다.
