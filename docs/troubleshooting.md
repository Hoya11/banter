# 트러블슈팅 기록

실사용과 코드 검수에서 발견한 문제, 진단과 개선 기록.

각 항목은 당시 관찰과 대응이다. 현재 구현 전체의 품질이나 지연을 보증하지 않으며,
현재 검증 범위는 [README](../README.md), 측정 조건은 [실험 기록](experiments/README.md)에 있다.
[실패와 개선 기록](failures.md): 주요 오류의 원인, 개선 내용과 검증 결과.

## 1. 대화가 끝나지 않고 무한히 이어짐
- **증상**: AI 둘이 멈추지 않고 계속 대화 — 비용·피로 누적
- **진단**: 라디오 모드는 의도된 기획이나, PRD가 예정한 세션 캡이 미구현 상태
- **개선**: max_turns 도달 시 마무리 인사 후 종료(`done`), FE 입력 비활성
- **결과**: 세션 경계 확보. 캡이 barge보다 우선하는 규칙도 이후 검수에서 보강

## 2. 말하는 중간에 채팅을 쳐도 대화가 안 끊김
- **증상**: AI 발화 중 입력해도 무시되고 발화가 끝까지 진행
- **진단**: 발화 스트리밍 도중에는 서버가 유저 입력을 수신하지 않는 구조
- **개선**: 스트림 task와 수신 task를 동시에 기다리고, 유저 입력이 먼저 오면 스트림을
  취소한 뒤 끊긴 지점까지만 기록
- **결과**: 텍스트 barge-in 동작. `—(끊김)` 표시로 실사용 확인

## 3. 채팅이 먼저 쌓이고 목소리가 뒤늦게 따라 읽음
- **증상**: 텍스트는 즉시, 소리는 수 초 뒤 — "말하는 주체가 목소리 나오기 전에 다음 채팅이 올라옴"
- **진단**: 텍스트(LLM 속도)와 음성(TTS+재생 속도)의 시간축 분리. 서버가 재생 상태를
  모르고 앞서 달림
- **개선**: 음성 동기 모드 — 자막은 오디오 재생 시점에 표시, FE의 played ack(seq 장부)을
  받아야 다음 턴 진행. "소리가 페이스메이커"
- **결과**: 재생 처리 확인에 맞춰 다음 턴을 진행. 중복 ACK는 같은 순번으로 처리하고 확인 유실에는 제한 시간을 적용한다. 실제 들은 구간과 대화 이력의 일치는 별도 과제다.

## 4. 소리가 아예 안 남
- **증상**: 자막만 뜨고 전 세션 무음 (특히 말 안 걸고 듣기만 할 때)
- **진단 1**: WS 프로토콜 변경 후 브라우저가 옛 FE를 캐시 — audio 이벤트 처리 코드 부재
- **진단 2**: unlock이 전송 버튼에만 걸려, 라디오 첫 오디오가 제스처 전 도착 →
  autoplay 차단을 조용히 스킵
- **개선**: index에 Cache-Control: no-store를 적용하고, 대화 시작 버튼의 사용자 동작 안에서
  무음 재생으로 오디오 권한을 확보. 실패하면 WebSocket 연결 전에 재시도 안내
- **결과**: 청취 전용 사용도 정상. 프로토콜 변경이 캐시로 조용히 깨지는 경로 차단

## 5. AI끼리는 빠른데 발화 사이가 너무 느림 (~8초)
- **증상**: 발화 하나 끝나고 다음 목소리까지 오랜 공백
- **진단**: 재생 종료 후에야 다음 턴(화자선정→생성→합성)을 시작하는 직렬 구조
- **개선**: 재생되는 동안 다음 AI 턴을 백그라운드에서 완성하고, 유저가 개입하면 폐기
- **결과**: 로컬 3턴 평균 2.09초를 관찰했다. 재생 확인부터 다음 오디오 도착까지이며, 대화 대기도 5초에서 1.5초로 바뀌어 사전 생성 단독 효과는 분리하지 못했다. [측정 조건](experiments/latency.md)

## 6. 내가 말하면 응답이 유독 느림 (5~8초)
- **증상**: AI끼리는 빠른데 정작 내 말에는 한참 뒤 반응
- **진단**: 유저 발화는 예측 불가라 prefetch 무효 + 발화 전체를 합성해야 첫 소리
- **개선**: Phase 3a 문장 단위 TTS — 첫 문장 완성 즉시 합성·재생, 나머지는 재생 중 준비
- **결과**: 텍스트 `say`부터 첫 오디오 도착까지 준비된 상태에서 약 2.4초를 관찰했다. STT를 포함하지 않아 남은 지연을 전사 탓으로 판단할 수 없다. 첫 실행과 제외 표본은 [지연 기록](experiments/latency.md)에 있다.

## 7. STT가 말하지도 않은 문장을 뱉음
- **증상**: `[stt] 전사: '친구들과 나누는 한국어 반말 수다...'` — 도메인 힌트 문장이 그대로 출력
- **진단**: 짧거나 조용한 입력에서 도메인 힌트와 같은 문장이 전사되는 현상을 관찰해 힌트를 원인 후보로 좁힘
- **개선**: prompt 힌트 제거 + 최소 녹음 길이 필터(서버 6KB/FE 8KB) + 전사 로그로 관측
- **결과**: 힌트 제거와 최소 길이 필터를 적용하고 전사 모델을 변경했다. 환각 제거율이나 인식률 개선을 비교 측정한 결과는 없다.

## 8. 마이크로 말해도 내 발화가 대화에 묻힘
- **증상**: 녹음→전사되는 사이 미리 준비된 AI 발화가 계속 나와 내 말이 뒤로 밀림
- **진단**: 서버는 유저가 말하려는 것을 전사 완료 전까지 모름 — 발화권 신호 부재
- **개선**: 마이크 버튼을 누르는 즉시 hold를 전송해 진행 중 발화를 중단하고 음성 데이터가
  올 때까지 새 턴 금지(대기 상한 15초). 브라우저 재생은 서버 응답을 기다리지 않고 중단
- **결과**: 전사 전에 발언권을 요청하는 경로를 추가했다. 서버 처리까지 0초라는 뜻은 아니며,
  아래 12번은 후속 검수에서 발견한 사전 생성 대기의 예외와 수정 기록이다.

## 9. 새로고침하면 서버가 크래시 로그를 쏟아냄
- **증상**: WebSocketDisconnect → RuntimeError('send once closed') 트레이스
- **진단**: prefetch 커밋 중 연결 끊김이 except Exception에 삼켜져 "준비 실패 폴백"으로
  오분류 → 닫힌 소켓에 재전송
- **개선**: WebSocketDisconnect는 re-raise — 폴백(준비 실패)과 종료(연결 끊김)는 다른 예외
- **결과**: 새로고침 시 조용한 세션 정리

## 10. ElevenLabs가 402 Payment Required
- **증상**: 크레딧이 있어 보이는데 모든 TTS 호출이 402
- **진단**: 당시 응답 본문이 `paid_plan_required`여서 잔여 크레딧 외에 선택한 보이스의
  이용 조건도 확인해야 함을 발견
- **개선**: 당시 계정에서 호출 가능한 기본 보이스와 모델 조합을 확인하고 청음으로 프리셋 선택
- **결과**: 해당 계정과 설정에서 음성 출력을 확인했다. 현재 무료 제공 범위나 모든 조합의
  이용 가능성을 뜻하지 않는다. [당시 비교 조건](experiments/tts-comparison.md)

## 11. 끼어들면 소리는 멈추지만 얼마나 빨랐는지 설명할 수 없음

- **증상**: 화면에서는 즉시 멈춘 것처럼 보여도 서버 로그에는 hold 수신과 생성 취소만 남아
  브라우저 재생을 언제 멈췄는지 확인할 수 없었음
- **진단**: 기존 played 신호는 정상 재생 완료, 중단, 대기열 폐기를 모두 같은 ACK로 처리해
  재생 중단 지표로 사용할 수 없었음
- **개선**: 마이크 버튼을 누른 시점부터 현재 Audio의 pause 적용까지 걸린 시간과 결과를 hold에
  함께 넣고, 같은 client event ID로 서버 이벤트와 연결. 재생 중단 성공만 지연 분포에 포함하고
  중단 실패, 대기열만 폐기, 재생 없음은 별도 건수로 분리
- **결과**: VAD 전환 전에 비교할 push-to-talk 기준 측정 도구를 확보. 실제 수치는 고정 시나리오를
  직접 실행한 뒤 [기준 측정 문서](experiments/push-to-talk-baseline.md)에 기록하기로 함

## 12. 미완료 사전 생성 대기 중 사용자 입력 지연

- **발견**: 2026-09-28 코드 검수 후 가짜 공급자와 메모리 소켓으로 재현
- **증상**: 현재 음성 처리와 참여 대기는 끝났지만 다음 사전 생성이 미완료일 때,
  `hold`와 새 텍스트가 수신 대기열에 남음. 사전 생성 완료 후 이전 맥락의 음성이 먼저 전송됨
- **진단**: `pre = await prefetch` 구간에는 일반 `_stream_turn`과 달리 병행 수신 작업이 없음
- **개선**: 사전 생성 완료와 입력을 함께 기다리고 동시 완료 시 입력 우선. hold는 턴 소모 없이
  기존 전사 대기로 인계하고 새 입력이 확정되면 이전 결과를 폐기
- **검증**: 처음 추가한 회귀 8개 중 수정 전 7개 실패를 확인하고 수정. 이후 수신과 세션 취소의
  경합을 보강한 [회귀 테스트](../server/tests/test_prefetch.py)로 입력, 복구와 종료를 확인
- **근거**: [재현 순서와 검증 범위](project-walkthrough.md#미완료-사전-생성-대기의-입력-지연).
  실제 목소리 테스트나 성능 측정 결과는 아님
