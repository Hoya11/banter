# 설계 결정 기록

## D-001. 파이썬 단독
실시간 음성·에이전트 생태계가 파이썬 중심(LiveKit Agents, Pipecat, LangGraph 네이티브).
언어를 섞기보다 생태계 정합성을 우선 — 프로젝트 하나에 목적 하나.

## D-002. 조립형 파이프라인 (STT+LLM+TTS, speech-to-speech 일체형 배제)
페르소나 2개 + 발화권 중재 + 끼어들기 제어에 파이프라인 통제력 필요.
일체형은 멀티 페르소나 중재 로직을 끼워 넣을 지점이 없음. 대가: 지연과의 싸움.

## D-003. 화자 선정 v1(supervisor 분리 호출) → v2(통합 생성) 단계 이행
처음부터 통합 생성으로 가면 품질 문제의 원인 격리 불가.
v1으로 기준선 확보 후, judge 점수 동등 이상일 때만 v2 이행 (Langfuse experiments 회귀 비교).

## D-004. 페르소나 데이터 주도 설계, 콘텐츠는 1쌍 시작
N쌍 전제로 구조 설계(설정 파일 분리), Phase 1~2는 대표 듀오 1쌍으로 품질 검증.
케미 튜닝은 쌍 단위로만 가능하므로 자유 조합은 배제.

## D-005. judge는 단일로 시작, 루브릭을 인터페이스로 고정
LLM-as-judge 1개로 채점 시작. 루브릭(채점 기준)과 채점 주체(심판)를 분리해,
점수 변동·편향이 문제되면 앙상블로 승격. 승격을 싸게 만드는 3가지 전제:
(1) 루브릭을 설정 파일로 분리, (2) judge 입출력 스키마 고정(항목별 점수+근거 JSON),
(3) judge 호출을 함수 하나로 캡슐화. D-003(supervisor v1→v2)과 동일 패턴 —
값싼 버전으로 시작하되 교체 지점을 미리 인터페이스화. 루브릭 초안은 엔진설계 §4.1.

## D-006. Phase 1 종료는 절대 컷오프로 판정
"버전 간 상승 추세"만으로는 첫 버전 go/no-go를 못 내리고 종료 시점이 무한정 늘어짐.
루브릭 항목 평균과 최저 항목에 절대 임계값을 건다(초안: 평균 7.0↑ & 6 미만 항목 없음).
임계값은 임의 초기값이며 조정 가능. 다만 컷을 사후에 낮춰 통과시키지 않도록 조정 이력을
experiments/에 남긴다. 없는 것보다 박아두는 게 자기기만·범위팽창을 막는다.

## D-007. 대표 듀오는 상반된 성격 대비형
냉소↔낙천처럼 기본 스탠스가 대비되는 1쌍. 반박·화제전환이 자연 발생해
"동의만 반복(루프)"이라는 1순위 실패모드(엔진설계 §1.4)를 구조적으로 방지.
동질형(비슷한 결)은 편안하지만 루프 위험이 커 배제. 구체 페르소나 프롬프트는 Phase 1 착수 시.

## D-008. Phase 1 대화 기록은 인메모리, 영속화는 Phase 2 이후
Phase 1 목적은 평가이지 기록 축적이 아님. judge/trace 데이터는 Langfuse에 남으므로
PostgreSQL과 기록 채널이 중복된다. DB 스키마 선행은 Phase 1 오버엔지니어링 —
인메모리 세션으로 실험 속도를 우선하고, 영속화 도입은 Phase 2~3에서 재검토.

## D-003 이행 완료 (2026-08-26) — supervisor v1 → v2(통합 생성)
게이트(judge 동등 이상, n=3) 통과로 이행:
- user_participates: v1 8.08 → v2 8.33 (user_inclusion 7.7→9.0)
- radio_long: v1 8.26 → v2 8.47 (context 8.3→9.0)
v2 출력 계약: 첫 줄 JSON 헤더(next_speaker/intent/topic) + 둘째 줄부터 대사.
규칙 가드·topic 갱신은 v1 코드 재사용, 헤더 불량 시 기계적 교대 폴백.
효과: 턴당 LLM 호출 -1 (supervisor ~1s가 유저 응답 임계 경로에서 제거, 비용 절감).
v1 경로는 폴백·비교용으로 유지.
