# 설계 결정 기록

## D-001. 서버와 평가 도구는 Python으로 통일

FastAPI 서버와 LangGraph 평가 그래프를 같은 언어로 구현해 상태, 프롬프트, 공급자
인터페이스를 공유한다. 브라우저의 마이크 캡처와 재생 제어는 JavaScript가 담당한다.
서버를 별도 언어로 분리하는 대안보다 현재 규모에서 코드와 검증 경로를 함께 관리하는 데
우선순위를 두었다. 언어별 성능 비교를 거친 선택은 아니다.

## D-002. STT, LLM, TTS를 분리한 조립형 파이프라인

사용자 1명과 AI 2명의 대화에서 화자 선정, 전사 확정, 발화 생성, 합성과 재생을 나누어
관찰하고 제어하기 위해 조립형을 선택했다. 공급자 오류와 지연이 어느 단계에서 발생했는지
구분하고, 단계별 공급자나 정책을 바꿀 수 있는 구조가 이번 프로젝트의 요구에 맞았다.

Speech-to-speech 일체형도 대안이다. 일체형에서 중재나 끼어들기 제어가 불가능하다고
판단한 것은 아니며, 같은 조건의 품질과 지연 비교 실험은 하지 않았다. 조립형의 대가는
단계 사이 대기와 직접 관리해야 하는 취소, 대기열, 오류 상태가 늘어난다는 점이다.

## D-003. 화자 선정 v1 분리 호출에서 v2 통합 생성으로 단계 이행

먼저 supervisor가 화자를 고르는 v1과 선택된 화자가 대사를 만드는 경로를 분리해
화자 선정과 대사 품질을 각각 점검했다. 이 기준선과 비교해 judge의 시나리오 종합점수가 동등 이상일 때
v2로 이행하는 게이트를 두었다. 통합 생성에서도 원인 분석은 가능하지만, 초기에는
각 단계의 입출력을 직접 확인하는 편을 택했다.

v1의 정상 턴은 화자 선정과 대사 생성에 LLM을 각각 한 번, 총 2회 호출한다. v2는 화자
정보와 대사를 한 출력에 담아 정상 턴의 생성 호출을 1회로 줄인다. 이 수에는 STT, TTS,
judge 평가와 재시도를 포함하지 않는다. v1 전략은 비교와 별도 실행을 위해 보존한다.

LangGraph는 `engine/eval/harness.py`에서 시나리오를 실행하는 평가 그래프에 사용한다.
실시간 API는 그래프의 공통 상태와 프롬프트 함수를 가져와 `api/app.py`에서 직접 조합하고,
입력 수신, 생성과 합성을 `asyncio`로 관리한다. 실시간 끼어들기를 LangGraph가 처리하는
구조로 설명하지 않는다.

## D-004. 페르소나 데이터 주도 설계, 콘텐츠는 1쌍 시작

향후 다른 듀오로 교체할 수 있도록 설정 파일을 분리하되, Phase 1~2는 대표 듀오 1쌍으로
품질을 검증한다. 페르소나의 말투, 성향과 목소리를 쌍 단위로 조정하기 위해 자유 조합은
현재 범위에서 제외한다. 여러 쌍의 동시 운영이나 자유 조합 품질을 검증한 상태는 아니다.

## D-005. judge는 단일로 시작, 루브릭을 인터페이스로 고정

LLM-as-judge 1개로 채점한다. 루브릭과 채점 주체를 분리해, 점수 변동이나 편향이
문제되면 여러 심판의 결과를 조합하는 방식을 검토한다. 이를 위해 루브릭을 설정 파일로
분리하고, 항목별 점수와 근거 JSON을 입출력 계약으로 고정하며, judge 호출을 함수로
캡슐화한다. 여러 심판을 호출하는 비용을 처음부터 부담하지 않되 교체 지점은 남긴다.
루브릭 초안은 [엔진 설계](engine-design-v0.1.md)의 4.1절에 있다.

## D-006. Phase 1 종료는 절대 컷오프로 판정

버전 간 상승 추세만으로 판단하면 종료 기준이 계속 바뀔 수 있어, 평균 7.0 이상이며
6 미만 항목이 없는 것을 초기 go/no-go 기준으로 정했다. 이 값은 제품 품질을 보증하는
외부 기준이 아니라 프로젝트의 초기 임계값이다. 조정한다면 실험 기록에 이유를 남겨
사후에 통과 기준만 낮추지 않도록 한다.

## D-007. 대표 듀오는 상반된 성격 대비형

냉소와 낙천처럼 기본 성향이 대비되는 1쌍으로 시작한다. 반박과 화제 전환이 나올 여지를
만들어 동의만 반복하는 실패를 줄이려는 선택이다. 비슷한 성향의 조합과 비교해 우월함을
입증한 것은 아니며, 대비형이라는 설정만으로 반복이 방지되는 것도 아니다. 실제 대화는
시나리오 평가와 프롬프트 조정을 통해 확인한다.

## D-008. 대화 상태는 인메모리, 영속화는 필요 시 검토

Phase 1은 사용자 기록 축적보다 평가에 초점을 두어 대화 상태를 메모리에 둔다.
judge와 trace는 설정 시 Langfuse에 기록하고, PostgreSQL을 별도로 도입하지 않았다.
세션 복원이나 사용자별 기록 보관이 필요해지면 영속화를 재검토한다. Phase 2~3에서
검토한다는 초기 계획은 DB 도입이 완료되었거나 필수라는 뜻이 아니다.

## D-003 이행 완료 (2026-08-26): supervisor v1에서 v2 통합 생성으로 전환

당시 n=3 비교에서 두 시나리오의 종합점수가 기존 이상이라는 프로젝트 게이트를 통과해 이행했다.

| 시나리오 | v1 종합 | v2 종합 | 항목별 기록 |
| --- | --- | --- | --- |
| user_participates | 8.08 | 8.33 | user_inclusion 7.7에서 9.0 |
| radio_long | 8.26 | 8.47 | context 8.3에서 9.0 |

이 결과는 [당시 judge 평가 기록](experiments/judge-scores.md)에 남은 소표본이다.
생동감 항목은 9.3에서 8.7로 낮아진 기록도 있다. 일반적인 품질 향상이나 모든 항목의
유지, 통계적 동등성을 입증한 결과로 확대하지 않는다.

v2 출력 계약은 첫 줄 JSON 헤더(`next_speaker`, `intent`, `topic`)와 둘째 줄부터의
대사다. 화자 규칙과 화제 갱신을 적용하며, 헤더가 잘못되면 기계적 교대로 처리한다.
이때 supervisor v1을 다시 호출하는 자동 폴백은 없다. 보존된 v1 전략과 v2의 헤더
오류 복구는 별도 경로다.

코드로 확인되는 변화는 정상 턴의 LLM 생성 호출이 2회에서 1회로 줄었다는 점이다.
기존 기록의 supervisor 약 1초는 당시 지연 구간의 추정값이며, 통합 생성으로 전체 응답이
정확히 1초 빨라졌다는 대조 실험 결과는 아니다. 별도 선정 호출을 없애는 구조적 효과와
실제 지연, 토큰 사용량, 총비용 변화는 구분한다.

## D-009. 생성 취소와 늦은 결과 격리를 함께 적용

사용자 입력 수신과 LLM 스트림 소비를 별도 `asyncio` 태스크로 실행한다. `hold`가 오면
진행 중인 생성 태스크를 취소하고 사용자 입력을 기다린다. 브라우저는 서버 응답을 기다리지
않고 먼저 현재 오디오를 멈춘다. 생성만 취소하는 방식으로는 이미 합성 중이거나 전송된
오디오를 막을 수 없으므로, 서버의 `tts_epoch`와 브라우저의 재생 세대, 순번 및 요청 ID로
늦은 결과도 격리한다.

`asyncio` 취소는 앱의 작업에 취소를 요청하는 동작이다. 원격 공급자의 연산이나 과금이
같은 순간 멈췄다는 보장은 없다. 이미 시작한 TTS 합성은 끝날 수 있으며, 이전 세대의
결과는 전송하지 않는다. 새 사용자 입력이나 재생 중단 표시로 문맥이 바뀌면 이전 사전 생성
결과를 폐기하고 갱신된 이력으로 답변 생성. `hold`만 수신하고 문맥 변화가 없으면 준비 결과 유지.

생성 완료와 입력이 동시에 준비되는 경우에는 완료된 생성을 먼저 비활성화한다. 가짜
공급자를 이용한 회귀 테스트로 이 순서와 늦은 합성 결과 폐기를 확인한다. 이는 상태 처리의
근거이며 실제 스피커 출력 중단 지연이나 공급자의 취소 비용을 측정한 결과는 아니다.
관련 구현은 [실시간 API](../server/api/app.py)와 [브라우저](../web/index.html)에,
측정 범위는 [push-to-talk 기준선](experiments/push-to-talk-baseline.md)에 있다.

## D-010. 오디오 순번과 처리 확인으로 다음 턴 진행 제어

서버는 오디오마다 `seq`를 붙이고 브라우저의 `played`를 받아 처리된 최고 순번을 관리한다.
생성 완료만 보고 다음 턴을 여는 대안 대신, 브라우저 처리 상태를 확인한 뒤 대화 간 대기
시간을 적용한다. 중복 확인은 최고 순번을 갱신하는 방식으로 처리한다. 확인이 오지 않을 때
영원히 기다리지 않도록 기본 30초 제한 후 장부를 갱신하고 진행한다.

`played`는 끝까지 들었다는 증명이 아니다. 정상 재생 완료뿐 아니라 중단, 오래된 오디오
폐기와 재생 실패에도 보내는 처리 확인이다. 순번만으로 실제 들은 단어를 복원할 수 없으며,
별도 `paused` 보고와 음성 순번으로 완성된 발화에도 중단 표시 반영. ACK 시간 초과는
실제 처리 확인과 구분하며, 생성된 전문은 보존. 단어별 청취 구간으로 자르는 기능은 미구현.
제한 시간 후 진행하는 정책도 완전한 재생 동기화보다 세션 복구를
우선하는 절충이다. [API 테스트](../server/tests/test_api.py)와
[브라우저 상태 테스트](../web/tests/index-state.test.mjs)에서 처리 확인과 중단 경로를 검증한다.

## D-011. 브라우저 VAD는 선택 옵션으로 추가하고 WebSocket 유지

발화마다 버튼을 누르는 동작을 없애기 위해 브라우저의 Silero VAD를 선택 모드로 추가했다.
`BANTER_INTERACTION_MODE=vad`는 `BANTER_STT_MODE=streaming_push_to_talk`와 함께 사용하며,
기본 실행은 기존 push-to-talk와 파일 전사를 유지한다. 서버 capability로 브라우저 모드를
선택한다. 확정된 말 시작은 공통 `hold`와 오디오 중단으로, 말 종료는 공통 PCM commit으로
연결한다. 마이크 청취 수명과 개별 발화 수명은 분리한다.

수동 버튼 유지, 음량 기준 감지, 서버 또는 공급자 VAD도 대안이다. 기존 브라우저 중단
경로를 활용하고 침묵 중 공급자 전송을 피하는 범위에서 실험하기 위해 브라우저 방식을
택했다. 말 확률은 화자나 참여 의도를 판별하지 않으므로 주변 음성, 짧은 맞장구와
스피커 에코로 불필요하게 끊길 수 있고, 침묵 판정은 문장 중간 종료를 만들 수 있다.

WebRTC는 감지 방식과 별도의 전송 선택이다. 현재 WebSocket을 유지하며, 전송 지연,
지터 또는 에코가 실제 병목으로 확인될 때 WebRTC나 LiveKit을 검토한다. 자동 테스트와
로컬 녹음 평가 도구는 마련했지만, VAD의 사용자 체감 효과와 환경별 오감지율을 비교한
실측 결과는 아직 없다. 선택 근거와 검증 범위는
[VAD 끼어들기 실험](experiments/vad-interruption.md),
[녹음 VAD 평가](experiments/vad-recording-evaluation.md)에 기록한다.
