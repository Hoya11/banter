# PRD v0.1 — 3자 음성 수다 서비스 banter

초기 기획을 보존한 문서. 아래 목표와 체크 항목은 현재 완료 현황과 구분.
현재는 WebSocket과 asyncio로 실시간 대화를 제어하고 LangGraph는 평가에 사용.
당시 계획의 LiveKit 전환과 영상 제작은 현재 개발 범위에서 제외.
[현재 구현과 검증](../README.md) / [후속 검증 계획](phase-3-plan.md)

> 왜 만드나: 기존 음성 AI는 대부분 1:1인데, 유저 1명 + AI 2명의 3자 대화에서 발화권 중재가 자연스러울 수 있을까가 궁금해서 시작한 실험. 이 문서는 범위 방어용 — 여기 없는 건 안 만든다.
> 상태: 초안. [결정 필요] 표시 항목은 확정 전.

## 1. 제품 정의

유저 1명 + AI 페르소나 2명이 실시간 음성으로 나누는 퇴근 후 수다.
유저가 말하지 않아도 AI 둘이 자연스럽게 대화를 이어가고,
유저가 대화 중간에 끼어들면(barge-in) 어색함 없이 화자가 양보하고 맥락이 이어진다.

핵심 차별점: 기존 음성 AI는 대부분 1:1이다. "3자 발화권 중재"가 이 프로젝트의 핵심 난이도이자 차별점.

## 2. 목표 / 비목표

### 목표
- G1. 3자 turn-taking 오케스트레이션을 LangGraph로 설계·구현하고 품질을 계량화한다
- G2. 실시간 음성 파이프라인의 지연·비용을 실측하고 최적화 과정을 기록한다
- G3. 평가 체계(시나리오 셋 + LLM-as-judge + Langfuse experiments)를 구축한다
- G4. 데모 영상 + 지표 패키지를 산출물로 남긴다 (README 최상단)

### 비목표 (안 한다)
- 무제한 공개 출시 (초대제 베타는 3단계 완료 후 별도 결정)
- 수익화, 결제
- 네이티브 모바일 앱 (웹 우선)
- 페르소나 자유 조합/커스터마이징/마켓플레이스 (듀오 "쌍 단위 선택"은 Phase 3 이후 확장 항목 — 아래 6.3 참고)
- 3인 초과 참여자 (유저 2명 이상, AI 3명 이상 등)

## 3. 단계별 범위 (사다리)

### Phase 1 — 텍스트 3자 엔진 (음성 없음)
가장 위험한 문제(발화권 중재)를 가장 싼 형태로 검증한다.
- 채팅 UI에서 유저 1 + AI 2 대화
  - AI 발화는 토큰 스트리밍으로 출력, 유저 입력창은 항상 활성 — 스트리밍 도중에도 개입 가능 (텍스트 barge-in 재현의 필수 전제, 엔진 설계 §2.1 참고)
- supervisor가 다음 화자 결정 (유저 침묵 시 타이머로 AI 턴 자동 재진입 = 라디오 모드)
- 유저 메시지 개입 시 화제 회수
- 대화 기록은 인메모리 세션으로 진행 (D-008), judge·trace는 Langfuse에 기록. PostgreSQL 영속화는 Phase 2~3에서 재검토 (아키텍처 §6.1 DB는 Phase 3 완성형 기준)
- 평가 시나리오 셋 v1 + LLM-as-judge 채점 + Langfuse 연동
- 종료 조건: "수다가 재밌는가" — judge 점수 + 본인 체감으로 go/no-go

### Phase 2 — 반이중 음성 (push-to-talk)
- 버튼 누르고 말하기 → STT → 엔진 → TTS 재생 (AI 2명 목소리 구분)
- TTS 후보 3~4종 청음 비교 (한국어 반말 수다 톤) → 기록 남김
- 구간별 지연 측정 시작 (p50/p95)

### Phase 3 — 전이중 barge-in
- LiveKit 기반 실시간 룸: VAD, barge-in(TTS 즉시 중단 + 맥락 롤백)
- barge-in 반응 시간 측정
- 비용 가드레일: 세션 캡, AI 발화 밀도 조절
- 데모 영상 촬영

## 4. 성공 지표 (측정 없으면 실패)

| 영역 | 지표 | 목표(가안) |
|---|---|---|
| 대화 품질 | 시나리오 셋 judge 점수 (루브릭 5항목 — 엔진설계 §4.1) | Phase 1 go 컷: 항목 평균 ≥ 7.0 & 최저 항목 ≥ 6.0 / 이후 버전별 상승 추세 |
| 지연 | 유저 발화 종료 → 첫 오디오 응답 p95 | < 1.5s (Phase 3) |
| 지연 | barge-in 감지 → TTS 중단 p95 | < 300ms (Phase 3) |
| 비용 | 대화 분당 원가 (STT/LLM/TTS 분해) | 실측 + 최적화 전후 비교 (Phase 2~3) |
| 안정성 | 세션 중 오케스트레이션 오류율 | 실측 기록 (Phase 1~3) |

## 5. 핵심 UX 시나리오 (Phase 3 기준)

1. 유저가 방 입장 → AI 둘이 인사하고 가벼운 화제로 시작
2. 유저 침묵 → AI 둘이 서로 주고받으며 대화 지속 (라디오 모드)
3. 유저 발화 시작 → 말하던 AI가 발화 중단(자연스러운 양보) → 유저 발언에 둘 중 적절한 쪽이 반응
4. 유저가 화제 전환 → 이전 화제를 억지로 끌지 않고 전환 수용
5. 세션 캡 도달 → 자연스러운 마무리 멘트 후 종료

## 6. 아키텍처

### 6.1 전체 구성 (Phase 3 완성형)

```
[웹 클라이언트 (Next.js)]
   │  WebRTC (audio)                │ REST/WS (세션, 기록)
   ▼                                ▼
[LiveKit Room] ◄──────────── [API 서버 (FastAPI)]
   ▲                                │ 세션/유저/대화기록/설정
   │ agent participant              ▼
[Agent Worker (Python)]        [PostgreSQL]
   ├─ STT 스트리밍 (외부 API)
   ├─ 3자 오케스트레이터 (LangGraph) ──► [LLM API]
   ├─ TTS 스트리밍 x2 보이스 (외부 API)
   └─ 트레이싱 ──► [Langfuse]
```

### 6.2 백/프 분리 원칙
- FE와 BE는 처음부터 별도 앱으로 분리 (모노레포 내 `web/`, `server/`)
- Phase 1~2: BE는 단일 파이썬 서비스 (FastAPI + LangGraph를 모듈로 내부 분리)
  - `server/api/` — 세션, 대화 기록, 설정
  - `server/engine/` — supervisor, 페르소나, 평가 하네스
- Phase 3: engine이 LiveKit agent worker로 물리 분리 (모듈 경계를 미리 그어두는 이유)
- FE 투자 최소화: 동작 증명 + 데모 영상 품질까지만. FE 코드는 AI 도구로 생성 위주

### 6.3 3자 오케스트레이터 (LangGraph) — 개요
- 상태: 대화 이력, 현재 화자, 유저 개입 신호, 화제 스택, 페르소나별 발화 카운트
- 노드(초안): 개입 감지 → 다음 화자 선정(supervisor) → 페르소나 발화 생성 → 발화 후 상태 갱신 → (침묵 타이머 시 AI 턴 재진입 루프)
- 상세 상태 설계는 Phase 1 착수 시 별도 문서
- 페르소나는 데이터 주도 설계: 코드가 아닌 설정(프롬프트, 보이스 ID, 관계성 정의, 화제 성향)으로 분리.
  듀오는 "쌍 단위"로 정의(케미 튜닝은 쌍 단위로만 가능). N쌍 전제로 설계하되 Phase 1~2는 대표 듀오 1쌍으로 품질 검증,
  쌍 선택 기능·2호 듀오는 Phase 3 이후 확장

### 6.4 기술 선택 및 근거
| 선택 | 근거 |
|---|---|
| 파이썬 단독 | 실시간 음성·에이전트 생태계(LiveKit Agents, Pipecat, LangGraph)가 파이썬 중심. 언어를 섞기보다 생태계 정합성 우선 |
| 조립형 (STT+LLM+TTS) vs speech-to-speech 일체형 | 페르소나 2개 + 발화권 중재 + 끼어들기 제어에 통제력 필요 |
| LiveKit (Phase 3) | 룸 모델이 멀티 참여자(유저1+AI2) 구조와 일치, barge-in/VAD 런타임 내장 |
| Langfuse | 기존 실무 경험, experiments로 회귀 평가 |
