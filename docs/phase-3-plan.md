# Phase 3 실행 계획 — 전이중(full-duplex) 실시간

> 목표: "유저 발화 종료 → 첫 오디오 p95 < 1.5s"(§3.1)와 "말만 하면 끊기는" barge-in.
> 착수 근거: push-to-talk 실사용에서 유저 응답 경로 5~8s 확인 ([latency.md](experiments/latency.md)).
> 원칙: 전송 계층과 무관하게 유효한 최적화(3a)부터 — LiveKit 전환(3c) 후에도 그대로 남는 것 먼저.

## 3a. 문장 단위 TTS 스트리밍 (현 WS 구조에서 즉효)
- LLM 토큰 스트림에서 문장 경계를 실시간 감지 → **첫 문장이 완성되는 즉시 합성·전송**,
  나머지 문장은 재생 중 뒤따라 합성 (§3.1 "문장 단위 flush")
- 기대 효과: 첫 소리까지 지연이 "발화 전체 생성+합성" → "첫 문장 생성+합성"으로 단축
- 유저 응답 경로(prefetch가 못 푸는 구간)에 직접 작용. FE는 문장 단위 자막 append
- 부가: 녹음 종료 즉시 "듣는 중…" 표시 (전사 공백의 인지된 지연 제거)

## 3b. 스트리밍 STT + VAD (push-to-talk 제거)
- 마이크를 상시 스트림으로 열고 **말하는 동안 전사** — 발화 종료 시점에 텍스트가 거의 준비됨
- VAD(음성 활동 감지)로 발화 시작/종료 판정 → 버튼 없이 말만 하면 됨
- endpointing 튜닝(§3.1: 300~500ms — 짧으면 말 끊는 AI, 길면 굼뜬 AI)
- backchannel 판별(§2.2): 맞장구("ㅇㅇ","그치")에는 발화권 유지

## 3c. LiveKit 전환 (WebRTC 전이중)
- 룸 모델: 유저 + AI 참여자, 실시간 오디오 트랙 (WS+base64 → WebRTC 스트림)
- **진짜 오디오 barge-in**: 재생 중 오디오를 VAD 감지 즉시 중단 + 재생 큐 flush + 맥락 롤백(§2.2)
- 에코 캔슬레이션(스피커 소리를 마이크가 다시 듣는 문제 — 전이중의 숨은 난관)
- 측정: barge-in 감지→중단 p95 < 300ms (PRD 지표)

## 마무리
- 지연·barge-in 실측 → experiments 기록 (전/후 비교)
- 비용 가드레일 재점검 (상시 STT 스트림은 비용 구조가 다름)
- **데모 영상** 촬영 → README 최상단
- 공개 전환 준비 (시크릿 스캔 → Public)

## 왜 이 순서인가
3a는 전송 계층 불문 유효 — LiveKit로 가도 그대로 쓰는 로직이라 낭비가 없다.
3b는 UX의 질적 전환(버튼 제거)이되 현 WS로도 가능. 3c는 전송 품질·에코·진짜 오디오
중단을 위한 마지막 계단. 각 단계가 독립적으로 배포 가능한 개선이라, 어디서 멈춰도
동작하는 제품이 남는다.
