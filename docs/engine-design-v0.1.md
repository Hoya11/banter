# 엔진 설계 v0.1 — 3자 turn-taking · 끼어들기 · 지연

이 문서는 초기 설계와 목표를 보존한 자료다. 아래의 맞장구 판별, 실제 들은 구간까지의
이력 반영과 지연 예산은 당시의 구현 계획과 목표다. 현재 구현, 평가용
LangGraph와 실시간 asyncio의 역할 및 남은 한계는 [문제 해결 사례](project-walkthrough.md)와
[README](../README.md)에 정리되어 있다.

> PRD 6.3의 상세 문서. 핵심 세 문제를 각각 상태/전이/측정으로 정의한다.
> 원칙: Phase 1(텍스트)에서 검증 가능한 것과 Phase 3(음성)에서만 검증 가능한 것을 구분해 표기.

## 1. 3자 turn-taking 엔진 [Phase 1 검증]

### 1.1 상태 스키마 (LangGraph state, 초안)
```
conversation:
  messages: [{speaker, text, ts, interrupted: bool}]
  topic_stack: [현재 화제, 보류된 화제...]      # 유저 개입 시 화제 회수용
turn:
  current_speaker: user | ai_a | ai_b | none
  consecutive_ai_turns: int                    # AI끼리 루프 방지 카운터
  last_user_turn_ts: ts                        # 유저 소외 감지
personas:
  ai_a / ai_b: {speak_count, last_stance}      # 발화 균형·입장 일관성
control:
  pending_user_input: text | none              # 생성 중 유저 개입 버퍼
  session_elapsed, budget_used                 # 세션 캡·비용 가드레일
```

### 1.2 노드 그래프 (초안, 화자 선정 v1 기준)
```
[입력 대기] ─ 유저 발화 ──► [개입 처리] ─► [화자 선정] ─► [발화 생성] ─► [상태 갱신] ─┐
     ▲       └ 침묵 타이머 ─► [화자 선정(AI턴)] ──────────────────────────────────┘
     └──────────────────────────────────────────────────────────────────────────┘
```
- 이 그래프는 v1(supervisor 분리 호출) 기준. v2 통합 생성(§1.3)에서는 [화자 선정]과 [발화 생성]이 한 노드로 합쳐진다
- 침묵 타이머: 유저 무발화 N초 → AI 턴 재진입 (라디오 모드). N은 튜닝 변수 (초안 4~7s, Phase 2에서 체감 조정)
- 세션 캡 도달 → 마무리 멘트 생성 노드로 분기

### 1.3 화자 선정 전략 — 단계적 이행
| 단계 | 방식 | 목적 |
|---|---|---|
| v1 | (a) supervisor 전용 LLM 호출: 이력·화제·개입 여부를 보고 다음 화자+발화 의도 결정 | 품질 기준선 확보, 판단 근거 로그 확보 |
| v2 | (c) 통합 생성: 발화 LLM이 next_speaker를 함께 출력, supervisor 호출 제거 | 턴당 호출 -1 (지연·비용 절감) |
| 게이트 | v1→v2 이행은 judge 점수 동등 이상일 때만 (Langfuse experiments 회귀 비교) | 호출 통합 전후의 대화 품질 비교 |

규칙 가드 (전략과 무관하게 항상 적용):
- 직전 화자 연속 발화 금지 (단, 짧은 보충 1회 허용은 튜닝 변수)
- 유저가 특정 AI를 지목/언급 시 해당 AI 우선
- consecutive_ai_turns ≥ K(초안 4~6) → 유저 소환 발화 강제 ("너는 어땠어?") — 단 소환 밀도 상한 (귀찮음 방지)
- speak_count 불균형 심화 시 소수 발화자 가중

### 1.4 자연스러움 실패 모드와 대응 [Phase 1 검증]
| 실패 모드 | 대응 |
|---|---|
| AI 둘이 서로 동의만 반복 (루프) | 페르소나에 상반된 기본 스탠스 + supervisor가 "반박/화제 전환" 의도 주입 |
| 유저 소외 (둘만 신남) | consecutive_ai_turns 가드 + 유저 관련 화제 회귀 |
| 화제 급발진/집착 | topic_stack — 전환은 수용하되 보류 화제 복귀는 확률적으로만 |
| 발화가 길어짐 (연설화) | 발화 길이 상한 (수다체 1~3문장), 프롬프트+후처리 이중 제어 |

## 2. 끼어들기 (interruption) 설계

### 2.1 텍스트 버전 [Phase 1]
- UI 전제: AI 발화는 토큰 스트리밍으로 표시하고 유저 입력창은 항상 활성. 일반 턴제 채팅(내 차례에만 입력)에서는 barge-in이 발생하지 않으므로, 스트리밍 중 개입 가능한 UI가 이 검증의 필수 조건이다
- AI 발화 생성 중 유저 메시지 도착 → 생성 태스크 취소, 미출력분 폐기
- 끊긴 발화는 messages에 interrupted=true로 잘린 지점까지만 기록
- supervisor는 "직전 발화가 끊겼음"을 프롬프트 컨텍스트로 받아 자연스러운 수습 생성
  (예: 끊긴 쪽이 "아 맞다 미안, 말해" 또는 그냥 유저 화제로 전환 — 매번 사과하지 않도록 변주)

### 2.2 음성 버전 [Phase 3]
상태 기계:
```
AI_SPEAKING ─ VAD 감지 ─► CANDIDATE (유저 음성 시작)
CANDIDATE ─ 짧고 무의미(맞장구) ─► AI_SPEAKING 복귀 (backchannel — 발화권 유지)
CANDIDATE ─ 지속/유의미 ─► BARGE_IN: TTS 즉시 중단 + 진행 중 LLM 턴 롤백 + 재생 큐 flush
BARGE_IN ─► USER_SPEAKING ─ endpoint ─► [개입 처리]
```
- backchannel 판별: 발화 길이(< ~600ms)·STT 부분 결과("ㅇㅇ","그치","진짜?")로 구분.
  짧은 맞장구로 AI 발화가 불필요하게 중단되는 상황을 줄이기 위한 설계
- 끊긴 지점 처리: 실제 발화된 오디오 지점까지만 대화 이력에 반영 (미재생 텍스트는 "말한 것"이 아님)
- 측정: VAD 감지 → 오디오 중단 p95 < 300ms (PRD 지표)

## 3. 지연 설계 [Phase 2~3]

### 3.1 유저 턴 응답 예산 (발화 종료 → 첫 오디오, 목표 p95 < 1.5s)
| 구간 | 예산(초안) | 비고 |
|---|---|---|
| endpointing (말 끝났다 판정) | 300~500ms | 응답 대기 시간과 발화 중간 절단 위험을 함께 고려해 조정 |
| 화자 선정 | 0ms (v2) / +1 호출 (v1) | v1은 소형 모델로 |
| LLM 첫 토큰 | 300~500ms | 컨텍스트 길이 관리 (이력 요약 압축) |
| TTS 첫 오디오 | 75~250ms | 저지연 모델 전제, 문장 단위 flush |
| 겹침 스트리밍 | -α | LLM 토큰 → 문장 단위로 TTS에 선전송 |

### 3.2 지연 은폐 기법
- AI-AI 턴 prefetch: 유저 침묵 구간의 다음 AI 발화는 미리 생성·합성해 캐시. 유저 개입 시 폐기.
  → AI 턴 사이 체감 지연을 0에 가깝게 줄이는 것이 목표이며, 실제 효과는 측정으로 확인
- 반응 필러: 유저 발화 직후 짧은 리액션("아 진짜?")을 저지연 경로로 먼저 재생, 본 응답은 뒤따라 재생.
  남용 시 부자연 — 확률적 적용 + judge 항목에 포함
- 이력 압축: 오래된 턴은 요약으로 치환해 LLM 입력 토큰 상한 유지 (지연·비용 동시 방어)

### 3.3 측정 체계
- 모든 턴에 구간별 타임스탬프 (Langfuse trace span으로 기록)
- 대시보드 지표: 구간별 p50/p95, barge-in 반응, prefetch 적중률, 턴당 비용
- 실험 기록은 docs/experiments/에 버전별 비교표로 누적

## 4. Phase 1 구현 순서 (제안)
0. 평가 기준 선행 확정: judge 루브릭 v1 + go/no-go 컷(4.1절). 주관적인 대화 품질을 일관되게 평가하고 종료 시점을 판단할 수 있도록 제품 코드 구현 전에 기준 확정
1. 상태 스키마 + 노드 그래프 골격 (발화 생성은 스텁)
2. 화자 선정 v1 (supervisor) + 규칙 가드
3. 대비형 듀오 1쌍(D-007) 프롬프트 초안 연결 → 수동 대화 테스트 (루브릭으로 자가 채점)
4. 끼어들기 텍스트 버전
5. 평가 시나리오 셋 v1 (끼어들기/화제전환/침묵/소외 각 3~5케이스) + judge 자동 채점 하네스 + Langfuse
6. go/no-go 판정 (컷 대조)

## 4.1 judge 루브릭 v1 + go/no-go 컷 [결정 반영: D-005·D-006]

채점 항목 (각 0~10, judge가 항목별 점수 + 근거를 함께 출력):
| 항목 | 무엇을 보나 | 관련 실패모드 |
|---|---|---|
| turn-taking 적절성 | 화자 교대가 자연스러운가 (연속발화·발화권 뺏김 없음) | §1.3 연속발화 가드 · §1.4 연설화 |
| 페르소나 일관성 | 두 AI의 대비된 스탠스가 대화 내내 유지되나 | 캐릭터 스탠스 붕괴 |
| 개입 시 맥락 유지 | 유저 끼어들기·화제전환에 자연스럽게 반응·연결하나 | §2.1 수습 실패 · §1.4 화제 급발진 |
| 대화 생동감 (anti-loop) | 동의 반복·단조로움 없이 티키타카가 사나 | §1.4 루프 |
| 유저 포함도 (anti-소외) | 유저를 대화에 끌어들이나 (둘만 신나지 않음) | §1.4 소외 |

- 입출력 계약(고정): `judge(transcript: [{speaker, text}], rubric_version) → { scores: {항목: 0~10}, reasons: {항목: string}, overall_comment }`
  → 이 계약과 루브릭이 D-005의 "인터페이스". 심판을 단일→앙상블로 바꿔도 불변
- go/no-go 컷 (초안): 5개 항목 평균 ≥ 7.0 AND 최저 항목 ≥ 6.0 → go
  → 임계값은 초기 임의값. 시나리오 셋 채점 결과에 따라 조정하며, 조정 근거와 이력은 experiments/에 기록
- 루브릭 항목 가중치·문항 표현은 튜닝 대상. 단 루브릭 변경 시 이전 버전 점수와 비교 불가해지므로 버전 태그를 붙여 Langfuse experiments로 분리 비교
- 평가 시나리오 케이스 형태(초안): 각 케이스 = { 초기 화제, 스크립트된 유저 발화·개입 타이밍, 기대 동작 }. 유저 입력과 개입 타이밍을 고정해 자동 채점 하네스에서 동일한 흐름을 재현 (상세는 phase-1-plan D 단계 착수 시)
